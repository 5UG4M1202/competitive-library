# 静的2次元 kd-tree の調査と設計案

矩形集約・点更新・最近傍・点列挙は [整数版](../library/geometry/integer_kd_tree.md) と [実数版](../library/geometry/real_kd_tree.md) として実装しました。下記は調査時の設計案であり、現在の詳しい仕様は各ページを参照してください。CC0 等のライブラリは公開された機能・仕様を調べる資料とし、そのコードをコピー・改変・移植していません。コードを採用する方針に変更する場合は、対象ファイルの来歴と条件を改めて確認します。

## 確認した資料

- [Nim-ACL の機能一覧](https://nim-acl.github.io/Nim-ACL/document_ja/index.html)：固定された多次元点に対する最近傍と直交範囲検索を提供し、`atcoder` 配下に CC0 と記載しています。Nim 用の別実装で、C++ の API や動作保証と同一とは限りません。
- [crvs/KDTree](https://github.com/crvs/KDTree)：BSD-3-Clause と明示された静的 C++ kd-tree。最近傍・半径・k 最近傍の機能があります。CC0 ではなく、ソースを使う場合は BSD-3-Clause の条件と各ファイルの来歴を確認する必要があります。README の最近傍に関する対数時間の表現を、任意入力の最悪保証として採用しません。
- [Maryland 大学の講義資料](https://www.cs.umd.edu/class/spring2022/cmsc420-0101/Lects/cmsc420-spring2022-lects.pdf)：標準的な空間分割と探索、最近傍の最悪時に多数の節点を訪れ得ることを説明しています。
- [Library Checker: Rectangle Sum](https://judge.yosupo.jp/problem/rectangle_sum)：半開矩形内の点の重みの総和を求めます。座標と重みが既知の静的問題です。これに通ることは、最近傍・点列挙・更新の検証を意味しません。

比較用に閲覧した [maspypy/library の kd-tree の公開仕様](https://maspypy.github.io/library/ds/kdtree/kdtree.hpp) には、半開矩形・同座標の点・元番号・最近傍探索があります。今回確認した範囲ではリポジトリのライセンスを確認できておらず、ライセンス明示済みの実装例としては扱わず、実装の流用もしません。

## 目的と初期 API 案

固定された整数2次元点集合に対し、構築後の複数クエリを処理します。`IntegerPoint` と入力順の `size_t` 番号を保持し、座標が同じでも異なる点として扱います。集合中の最近点対を一度求める既存 `closest_pair` とは用途が異なります。実数座標版も2次元で提供し、高次元化は別途検討します。

1. `nearest(query)`：最も近い点の元番号と距離の二乗。空集合は `optional` の空。複数候補が同距離なら任意の1点を返し、順序を保証しません。自己点を除外する用途は、番号指定による除外を設けるか別途検討します。
2. `for_each_in_rect(xl, xr, yl, yr, visit)`：半開矩形 `[xl,xr) × [yl,yr)` の点の元番号をコールバックに渡します。結果の順序は未規定。空矩形は0件。列挙途中の停止や vector を返す補助は必要性を見て決めます。
3. `count_rect(...)`：同じ半開矩形に含まれる点の数。同座標の点はそれぞれ数えます。

現在の `nearest` と `for_each_in_rect` は各ヘッダーの説明を参照してください。`count_rect` は独立 API としては未実装で、各点に値1を割り当てた加算 Monoid の `prod` を使えます。整数の矩形端点は `IntegerWide` を採用し、最大座標を含める際は `max + 1` を狭い型で計算しません。

## 構築・探索・計算量

- 中央付近で左右に分ける平衡な静的木を作り、部分木ごとの点を囲む閉矩形と点数を保持する案です。分割軸と同座標の扱いは決定的にし、極端な重複でも構築が進むようにします。子や点は配列で所有し、参照先の寿命に依存しません。
- 範囲検索では、部分木の矩形がクエリと交わらなければ枝刈りし、全体が含まれる場合は個数をまとめて足します。列挙は実際に返す点数 `k` の費用が必要です。
- 最近傍では、点と部分木の矩形の最小距離を下界とし、現在の最良候補より改善できない部分木を除きます。同距離候補の扱いと枝刈り条件は整合させます。空木は番兵距離ではなく候補の有無で表します。
- 標準的な条件を満たす2次元 kd-tree には、直交矩形の報告で `O(sqrt(n)+k)` といった評価があります。ただし、分割・重複・保存方式に関する仮定をこの実装案でまだ証明していません。公開 API の保証は保守的に最悪 `O(n+k)`（数え上げは `O(n)`）とし、より強い評価を記すなら仮定と証明を別途用意します。最近傍は最悪 `O(n)` です。
- メモリは点・節点・部分木情報で `O(n)` を目標とします。中央要素選択に `std::nth_element` を使う場合、標準の平均線形計算量を前提とした構築時間と、最悪時の保証を区別します。再帰深さや一時確保も計測します。
- 箱への距離と点間距離は、座標差を広い型に変換してから計算し、積・和も `IntegerWide` に収まることを要求します。`__int128_t` は GCC/Clang の拡張で、MSVC 非対応です。

## 集約・更新と他の選択肢

点数や重みの矩形集約は、各部分木にその点の値の集約を保持することで可能です。交差しない部分木は単位元、全体が含まれる部分木は保存済み集約を使い、それ以外は子に分けて結合します。走査順に依存しないため、結合則・単位元のほか、通常は可換性が必要です。非可換演算や訪問順を意味づけた API を暗黙に約束しません。和・min・max・gcd・bitwise・最小値と回数などを共通のインターフェースで扱う案とし、まずは点数と加算を検証します。点の値の上書きと値への操作は区別し、重みの和の型とオーバーフローも呼び出し側の制約です。

実用上は、理論上の最悪ケースを理由に消極的になるのではなく、木のバランス、部分木矩形による枝刈り、全域包含時の集約、内部の確保回数を確認します。候補に近い子から探索する方法や葉に複数点を持たせる方法は性能候補とし、点集合・クエリ形状を変えた比較で判断します。故意に特定の実装を狙わない入力でも、一直線・同座標・細い矩形などは普通に現れ得るため、これらを必須の検証対象にします。大きな入力への実測結果と制限時間を記録し、任意の入力での高速性は保証しません。

登録済み点の重み変更は、点番号と葉・親の対応を持てば座標を変えずに別機能として追加できます。新しい座標の挿入や削除は静的版では扱いません。オフラインで更新予定座標をあらかじめ登録する解法は可能ですが、完全にオンラインの新座標追加とは区別します。

矩形和だけで最悪時計算量が厳しい場合は、座標圧縮とオフライン走査、2次元 range tree や wavelet matrix なども候補です。kd-tree の実測速度だけでこれらに常に優ると約束しません。

## 最近傍と点列挙の追加後の測定

整数版・実数版とも、入力番号の対応を節点本体とは別の配列に保持します。2026-11-03 に GCC 11.4 `-O2`・WSL2、Ryzen 7 5800X で、同じ20万点・20万矩形集約クエリを追加前後のバイナリで各1回実行しました。最大 RSS は入力や構築時の領域を含みます。

| 配置・型 | 追加前の全クエリ | 追加後の全クエリ | 最大 RSS の前 → 後 |
| --- | ---: | ---: | ---: |
| ランダム・整数 | 59 ms | 61 ms | 28.3 → 29.8 MiB |
| 格子の細い縦帯・整数 | 736 ms | 724 ms | 28.3 → 29.8 MiB |
| ランダム・実数 | 120 ms | 119 ms | 37.7 → 39.2 MiB |
| 格子の細い縦帯・実数 | 1,937 ms | 1,752 ms | 37.7 → 39.2 MiB |

いずれも1回の参考値であり、実行時の揺れを含みます。別途 `tools/benchmark_kd_tree_search.cpp` の固定乱数による20万点・2万クエリでは、整数版の最近傍約12 ms・矩形列挙約5 ms、実数版は約29 ms・約10 msでした。小さな矩形中心の例で、偏りのある入力・大きな出力・任意入力の速度を保証しません。

## 矩形集約の初期実装の測定

`tools/benchmark_integer_kd_tree.cpp` を GCC 11.4、`-O2`、WSL2 上で実行した、端点処理を改良する前の一例です。各ケースは20万点・20万クエリ、値は `long long` の和です。`/usr/bin/time` の最大 RSS は入力とプログラムも含みます。機械や負荷で値は変わり、性能保証ではありません。

| 点配置とクエリ | 構築 | 全クエリ | 最大 RSS |
| --- | ---: | ---: | ---: |
| ランダム点、狭い正方形 | 59 ms | 103 ms | 約 27 MiB |
| 格子、幅1の縦帯 | 41 ms | 1,890 ms | 約 27 MiB |
| 横一直線、幅100 | 20 ms | 144 ms | 約 27 MiB |
| 10座標に重複、1座標を指定 | 36 ms | 45 ms | 約 27 MiB |

格子の細い帯では他の例より負荷が大きく、意図的なハックでなくても分布・矩形形状が性能に影響することを示します。訪問節点数や別実装との比較は未測定です。固定の例だけで、任意入力や最近傍検索の性能は推測できません。

端点処理の改良後、同じ環境で Library Checker Rectangle Sum の生成済み公式14ケースの出力を全て期待出力と照合しました。最大ランダム3件は約6.7〜7.8秒、座標集中3件は約6.6〜6.8秒、最大 RSS は約27 MiBでした。ローカルでは他のテストも並行していたため厳密なベンチマークではありませんが、問題の制限時間5秒を超えており、公式環境での時間内通過は確認できていません。入出力・探索・配置の改善と、条件を揃えた再測定が残っています。

### コンパイラ設定と節点配置の調査

2026-11-02 に同じ WSL2、Ryzen 7 5800X、GCC 11.4 で、公式ケースを Linux の一時領域へコピーし、他の検証と並行せずに測定しました。入出力を含む各2回の経過秒数です。CPU 周波数や他プロセスの影響を排除した厳密な比較ではありません。`-march=native` は計測した実行機に合わせる設定で、別 CPU 上では互換性も速度も同じとは限りません。

| 設定 | 最大ランダム `max_random_00` | 座標集中 `xy_concentrate_00` |
| --- | ---: | ---: |
| `-O2` | 5.63, 5.31 | 5.09, 5.84 |
| `-O2 -march=native` | 6.90, 5.92 | 6.20, 6.77 |
| `-O3 -march=native` | 5.39, 5.20 | 5.60, 5.69 |

この測定では最適化オプションを増やすだけで一貫した改善は確認できませんでした。実行環境差も大きいため、5秒という問題の制限とローカル時間を直接比較して公式環境の判定を予測することもできません。[Library Checker の公開言語設定](https://github.com/yosupo06/library-checker-judge/blob/master/langs/langs.toml) では C++20 に GCC 15.2 と `-O2 -march=native` を指定しています。ここで測ったローカルの GCC 11.4 とは異なります。

部分木への訪問数を数える一時的な計測版では、それぞれ20万クエリに対して約3.10億節点、平均約1,548節点／1,545節点、1クエリ最大4,800／4,706節点でした（存在しない子は数えない）。各分布での実測値であって、計算量の一般的な保証ではありません。

点座標の別配列をたどらず節点に置く試作を、同じ2ケースで交互に各2回実行しました。最大ランダムは元の 7.12・5.96 秒に対し 5.05・5.04 秒、座標集中は元の 6.17・6.36 秒に対し 4.10・4.24 秒でした。試作の最大 RSS は約 28.4 MiB、元は約 26.9 MiB で、入力と構築時の一時領域を含みます。これを受け、現在の実装は座標を節点に保持し、構築用の座標コピーは構築後に解放します。上記は解放を追加する前の試作の値であり、速度保証ではありません。最近傍・列挙は対象外です。

確定版の `-O2 -march=native` による単独再測定は、最大ランダム 3.90・4.22 秒、座標集中 4.37・4.62 秒、最大 RSS は約 28.4 MiB でした。時間の変動があるため試作前後の比率を精密な改善率とは扱いません。確定版の公式14ケースはすべて期待出力と一致していますが、公式サーバーへの提出・時間内通過は未確認です。

## 検証計画

- 空・1点・同座標・全点一致・縦横一直線・格子・偏った分布、最小／最大座標、空矩形と各辺上、全点内包・全点外を検証します。
- 最近傍・列挙・個数・加算は、小さい入力で全点走査と多数の seed 固定ランダム比較を行います。同距離の解は返された点と距離の正しさを検査します。
- 大規模な格子、集中点、縦横の帯、点ごとの矩形・最近傍などで構築時間、探索時間、ピークメモリ、訪問節点数を測ります。クエリの形状とデータ分布を併記します。
- judge-backed 検証は問題の入出力と端点に合わせて別テストを作り、重み和なら Rectangle Sum、範囲列挙なら対応問題を確認します。LC の点更新矩形和を使う場合、事前登録と真のオンライン挿入の違いを示します。使わない操作の検証済み表示はしません。
